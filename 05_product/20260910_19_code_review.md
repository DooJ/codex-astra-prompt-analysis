# 19. 코드 리뷰의 판정·우선순위·출력

분류: 검토자 역할 전용 지침 · 기준: 2026-09-10 공개 판본

이 문서는 공개 자료의 해설이며, 현재 환경에 실행 지침으로 설치된 문서가 아닙니다.

## 어떤 상황을 다루는가

코드 변경을 검토하면서 실제 수정할 가치가 있는 결함을 찾고, 그 영향과 위치를 재현 가능한 근거로 전달하는 절차다.

## 원문에서 정리한 결함 기준

- 정확성, 성능, 보안 또는 유지보수에 의미 있는 영향을 주는 문제인가.
- 하나의 구체적인 문제로 설명하고 수정할 수 있는가.
- 해당 변경에서 새로 생긴 문제인가.
- 작성자가 알았다면 수정할 가능성이 있는가.
- 확인되지 않은 의도나 환경을 가정해야만 성립하는 주장은 아닌가.
- 다른 부분이 영향을 받는다면 실제 영향받는 코드를 제시할 수 있는가.
- 의도적인 동작 변경을 결함으로 잘못 판단한 것은 아닌가.

사소한 취향 차이는 기본적으로 지적하지 않지만, 문서화된 프로젝트 규칙을 위반하거나 이해를 방해한다면 별도로 판단한다.

## 처리 흐름

1. 리뷰 대상이 현재 변경인지, 기준 브랜치와의 차이인지, 특정 커밋인지 확인한다.
2. 적용되는 프로젝트 규칙과 변경 내용을 함께 읽는다.
3. 실제 결함 후보와 발생 조건을 확인한다.
4. 같은 위치·같은 원인의 중복 지적을 합친다.
5. 영향에 맞는 우선순위와 간결한 설명을 작성한다.
6. 전체 변경의 정확성에 대한 판단을 정해진 형식으로 반환한다.

## 우선순위와 출력

P0는 광범위하게 작업이나 사용을 막는 긴급 문제, P1은 빠른 수정이 필요한 문제, P2는 일반적인 수정 대상, P3는 낮은 우선순위로 설명된다.

각 지적에는 제목, 왜 문제인지, 발생 조건, 코드 위치와 필요할 경우 적용 규칙의 근거를 연결한다. 과장하지 않고 검토자가 빠르게 이해할 수 있는 짧은 문단으로 작성한다.

## 예외와 경계

이 템플릿은 변경 리뷰를 전제로 하므로 기존 결함을 새 변경의 결함처럼 지적하지 않는다. 프로젝트 전체 결함 감사와는 범위가 다르다.

수정할 가치가 있는 결함이 없으면 억지로 지적을 만들지 않는다. 여러 문제가 확인되면 첫 문제에서 멈추지 않고 각각 정리한다.

출력 JSON 구조와 인라인 코드 위치는 리뷰 제품에서 소비하는 형식이다. 검토 결과가 수정 코드의 적용을 의미하지는 않는다.

## 이해를 위한 사례

“이 코드가 위험해 보인다”보다는 특정 입력에서 반환값이 잘못되고, 해당 호출자가 그 값으로 잘못된 상태를 저장한다는 근거를 제시한다. 설명용 사례다.

## 재사용 관점

결함의 실제 영향, 발생 조건, 수정 가능성과 근거를 갖추는 원칙은 일반 검토 업무에도 활용할 수 있다.
