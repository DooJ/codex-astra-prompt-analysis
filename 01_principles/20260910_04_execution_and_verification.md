# 04. 실행과 검증

분류: 공통 실행 원칙과 개발 도구 규약 · 기준: 2026-09-10 공개 판본

이 문서는 공개 자료의 해설이며, 현재 환경에 실행 지침으로 설치된 문서가 아닙니다.

## 어떤 상황을 다루는가

자료를 찾고 실제 변경을 수행할 때 낭비를 줄이며, 결과가 요청을 충족했는지 확인하는 방법이다.

## 원문에서 정리한 규칙

- 파일·문자열 검색에는 빠른 검색 도구를 우선 사용한다.
- 서로 독립된 조회는 묶어 실행할 수 있지만, 앞선 결과에 의존하는 행동과 변경 작업은 순서를 유지한다.
- 필요하지 않은 출력과 반복 조회를 줄인다.
- 명령 문자열은 실행 코드로 취급한다. 문자열 직렬화를 셸 이스케이프와 혼동하지 않는다.
- 기존 코드의 방식과 작업 범위를 존중하고, 불필요한 복잡성과 관련 없는 수정을 늘리지 않는다.
- 변경에 맞는 테스트와 검사를 선택한다. 결과가 통과한 뒤 추가 변경이나 불확실성이 없다면 검증을 계속 늘리지 않는다.
- 테스트가 통과했다는 사실만으로 넓은 요구사항 전체가 충족됐다고 주장하지 않는다.

## 처리 흐름

1. 필요한 자료와 현재 상태를 확인한다.
2. 조사 항목을 독립 작업과 의존 작업으로 구분한다.
3. 요청 범위에 맞는 변경을 수행한다.
4. 변경된 동작을 직접 확인하는 검증을 실행한다.
5. 검증 범위와 실제 요구사항을 대조한다.

## 다른 템플릿 사이의 차이

상단의 기본 지침은 영향이 작은 가역적 변경에 불필요한 테스트를 만들지 않도록 한다. 뒤쪽 엔진 기본 템플릿에는 승인 모드에 따른 테스트 실행 시점, 별도 요청 없는 커밋·브랜치 생성 제한 등 다른 규칙이 있다.

따라서 이 항목은 모든 조각을 동시에 적용한 단일 개발 절차가 아니다. 현재 적용할 템플릿을 선택한 뒤 검증 수준과 권한을 결정해야 한다.

## 이해를 위한 사례

오탈자를 바꾸는 작업과 결제 금액 계산을 바꾸는 작업의 검증 범위는 달라야 한다. 후자는 경계값과 기존 동작을 확인하는 근거가 필요하다. 이는 업무 차이를 설명한 사례다.

## 재사용 관점

검색 도구 이름은 교체할 수 있다. “독립 조회만 병렬화하고, 변경 영향에 비례해 검증하며, 확인한 범위만 주장한다”는 원칙이 핵심이다.
